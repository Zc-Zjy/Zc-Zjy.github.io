Java高并发秒杀的设计原则

十七2025-10-112025-10-11


一、前言

你有没有经历过这样的场景？
（1）凌晨12点，iPhone新品发售，你守在手机前，手指紧贴屏幕；
（2）倒计时结束，点击“立即抢购”，页面卡住、按钮无响应、提示“库存不足”；
（3）刷新一看，商品已经售罄——但你根本没成功下单。

这就是典型的高并发秒杀场景。它不仅仅是“卖东西”，更是对系统架构的极限挑战。

1、什么是秒杀？

秒杀，是指在极短时间内（通常几秒到几分钟），大量用户集中访问并尝试购买限量商品的行为。其核心特征是：
（1）瞬时高并发：10万+用户同时发起请求；
（2）资源有限：商品库存可能只有100件；
（3）强一致性要求：不能超卖、不能重复下单；
（4）用户体验敏感：页面卡顿、失败提示都会影响口碑。

2、为什么普通系统扛不住？

想象一下：10万人在同一毫秒点击“抢购”，如果系统不做任何优化，所有请求直接打到数据库，会发生什么？
（1）数据库连接池瞬间耗尽；
（2）MySQL锁竞争激烈，事务排队；
（3）CPU飙升，响应延迟从几毫秒变成几秒甚至超时；
（4）最终结果：系统崩溃、库存超卖、订单错乱。
这就像双十一零点的超市收银台——只有一个收银员，却有上万人排队结账。

1、按钮防重复点击（防误触）

这是最基本也是最重要的防护措施。用户手滑连点，会生成大量无意义请求。

（3）请求失败后禁用按钮防止重复提交。

2、请求频率限制（节流）

即使有人使用脚本刷请求，前端也应尽可能做初步限制。

3、防抖 vs 节流

1、防抖（debounce）
适用场景：搜索框输入，停止输入后才触发。

2、节流（throttle）
适用场景：秒杀按钮，固定频率执行。

3、注意：节流只能防“正常用户误操作”，无法防御恶意脚本攻击。但它是多层防御的第一环。



三、后端优化

1、流量削峰：使用Redis Streams实现请求缓冲

1、设计目标
（1）防止瞬时百万级请求打爆数据库；
（2）实现“削峰填谷”，平滑消费请求；
（3）支持失败重试与消息确认机制。

2、架构角色
（1）生产者：用户点击抢购 → 写入Redis Streams；
（2）消费者组：多个服务实例组成消费者组，竞争消费；
（3）ACK机制：成功处理后确认，防止消息丢失；
（4）死信队列（DLQ）：处理失败消息，支持人工干预或延迟重试。

3、完整实现流程

4、优势总结
（1）支持多消费者组负载均衡；
（2）ACK 机制保障消息不丢失；
（3）可通过XPENDING查看待确认消息；
（4）支持从任意位置重新消费。

3、防重复下单：幂等性 + 分布式锁

1、为什么需要防重复？
（1）用户手滑连点；
（2）网络超时导致前端重试；
（3）脚本恶意刷单。

2、方案选择：业务幂等校验为主，分布式锁为辅

方案 适用场景 性能 推荐度
Redis 是否已参与 第一道防线 中 ⭐⭐⭐⭐
数据库唯一索引 最终防护 中 ⭐⭐⭐⭐
Token 校验机制 前端防刷 高 ⭐⭐⭐⭐
Redis 分布式锁 高并发抢购 高 ⭐⭐⭐

方式一：Redis 记录“已参与”（最快）
在 Redis 中记录“用户A已参与iPhone秒杀”，用完即焚，活动结束后自动过期。

快，不依赖数据库，高并发防重第一道防线。

方案二：数据库唯一索引（最终一致性保障）

同一个用户在同一个活动里只能下一单，但可以参加不同活动，或活动结束后正常购买。

方案三：Token 机制（防止脚本刷单）
每次抢购前必须先获取一个“令牌”，用完即失效，防止机器人无限刷。
